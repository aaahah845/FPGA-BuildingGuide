# 动态文字修改交接（2026-10-12）

## 需求和版本边界

用户希望标题和房间名称能自由输入新的汉字。本副本同时放开楼层名、简介和活动文字，电脑端生成本次所需字模。运行时仍由 FPGA 完成文字查表与像素合成；电脑仅负责离线素材准备。

源副本为 `lab_image_title_config_20261012`。它基于外接按键 seed61 工程，但标题副本本身尚未上板。本次也必须单独上板，不能引用旧 seed61 的 30 分钟测试作为新版本实测结果。原文件保护证据为 `reports/dynamic_text/baseline_sha256.json`，最终位流、资源与时序结论见 `release/candidate_manifest.json`。

## 数据流

`runtime_site.json → export_site_cfg.py → SITE.CFG v6 → SD 文件读取 → 配置 RAM + 原字模 RAM → config_ready → 视频域复制配置 → site_ready → 正常场景`

v6 固定 27648 字节，前 8192 字节保留原配置布局；后 19456 字节装载两套完整字模。配置与字模分别校验。字模不经过新 staging RAM，直接从 SD 时钟域写入已有 BRAM；读端仍为视频时钟，保持原来的单拍延迟。

## 修改的 RTL

| 文件 | 作用 |
|---|---|
| `SD/sd_site_assets.v` | 只接受完整 v6 文件，读取 54 扇区；配置写入仅限前8KB，后续拼装为5632个字模存储字；双校验通过后发ready；读配置遇文件系统错误时abort并报9，避免永远等待file_end |
| `guide_large_font.v` | 原128字24×24打包字库增加SD时钟写端，原8块BRAM布局保持 |
| `room_notes_font.v` | 原96字16×16说明字库增加写端，原3块BRAM布局保持 |
| `guide_scene_compositor.v` | 分发字模写地址到两字库，拒绝超出5632的地址；像素流水线未加级 |
| `top_tf_hdmi_audio.v` | 连接资源管理器字模写端与合成器，写时钟使用同一sd_card_clk；配置完成前最终RGB置黑，垂直同步期开放显示，同步信号继续运行 |
| `site_runtime_wiring.vh` | v6使用规范8KB布局，移除旧格式重映射；完整复制配置之后才拉高site_ready |

固定小字 `guide_font_rom.v`、图片调度/预加载、SDRAM读控制器、按键映射、引脚约束和时钟参数均未改。

## 字库容量和复位契约

名称字库固定保留ID0、29、30、56、57、58、59，供空白和原默认标题复用。其余121槽动态分配。说明字库固定保留ID0及19..28，其余85槽动态分配。导出器保留固定字位图，闲置动态字清零，并用字体cmap检查新字是否存在。

RAM不会因逻辑复位恢复initial。每次启动必须重装完整字模，所以新位流明确拒绝旧V5配置，不提供“靠初值回退旧字库”的不可靠兼容。当前仅支持统一复位后开机加载，不支持只复位SD域或运行中热更新。字体写入阶段不允许用户操作；完成后字模RAM只读。

## 验证覆盖与限制

- 导出器验证长度、字符容量、缺字、固定字模保留、24px打包、校验和、生成文件版本以及重复导出确定性。
- 字库仿真验证全部行、bank、异步写读、原读延迟和实际合成器写端分发。
- 配置仿真使用真实资源管理器状态机和配置RAM，替换文件系统输出，覆盖有效包、热复位换字体、valid空洞、截断、损坏、旧版本、无file_end的文件系统错误等情况。
- 启动门控测试从当前top提取实际逻辑，连接真实RGB转AXIS模块；检查4800个有效像素，确认中途ready不会提前显示，且valid/user/last与未遮挡参考完全一致。
- 原标题像素回归验证未启用写端时的原合成流水线；这是像素逻辑回归，不代表新v6位流兼容旧配置。记录中的16次扫描是帧片段，不能称为16个完整1080p帧。
- FAT/SPI物理读卡、真实HDMI效果和按键功能仍需上板核对。静态时序是否闭合必须看新报告，不能用原有功能测试替代。

无需因上述限制重复修改已通过测试的像素流水线。后续首先使用新位流与匹配v6配置做上板验证，再决定是否发布。
